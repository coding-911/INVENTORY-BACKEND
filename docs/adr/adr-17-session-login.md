# ADR-17 인증 방식: 세션 로그인

> 원본(노션): https://app.notion.com/p/423b82ca31e581d4b8a6d27b90a1ebf0  
> 내보낸 날짜: 2026-11-25. **노션이 원본이다.** 이 파일과 노션이 다르면 노션을 따른다.  
> 상태: 채택 (2026-11-25). 영역: 백엔드, 프론트엔드, DB. ADR-11 "인증 방식: OAuth2 + JWT"를 대체한다.

## 1. 배경: ADR-11을 바꾼 실제 원인

로그인 기능을 만들기 시작하면서(2026-11-25) ADR-11(OAuth2 Authorization Code + PKCE, access token은 브라우저 메모리, refresh token 7일은 HttpOnly 쿠키)을 Spring Security 7의 인가 서버로 구현하려 했더니 문서대로는 되지 않는 점 두 가지가 드러났다.

1. **refresh token을 HttpOnly 쿠키로 줄 수 없다.** Spring Authorization Server는 비밀키 없는 브라우저 앱(공개 클라이언트, PKCE)에는 기본적으로 refresh token을 발급하지 않고, 발급하더라도 토큰 응답 본문(JSON)에 담는다. ADR-11대로 하려면 발급 조건, 응답에서 빼서 쿠키로 옮기기, 갱신 때 쿠키에서 읽기를 각각 Spring 확장 코드로 만들어야 했다.
2. **로그인 화면이 인가 서버 주소에 있어야 한다.** Authorization Code 흐름은 브라우저를 인가 서버로 보내 그곳의 로그인 화면에서 아이디·비밀번호를 받는다. 그래서 React 화면이 아니라 백엔드에 로그인 화면(Thymeleaf 등)을 따로 만들어야 했다.

이 두 가지를 보고 BFF(백엔드가 토큰을 서버에 들고 브라우저에는 세션 쿠키만 주는 방식)로 바꾸기로 했다. 그런데 우리 백엔드는 인가 서버·API·BFF가 모두 **앱 하나**다. 앱 안에서 OAuth2 토큰을 주고받으면 자기 자신에게 토큰을 발급하는 셈이라, BFF의 결과는 서버 세션 로그인과 같다. 그래서 OAuth2·JWT·인가 서버를 쓰지 않는 세션 로그인으로 정했다.

## 2. 결정

| 항목 | 결정 |
|---|---|
| 방식 | 서버 세션 로그인. 프론트 로그인 화면이 `POST /api/v1/user/login`으로 아이디·비밀번호(JSON)를 보내면 서버가 세션을 만들어 HttpOnly 쿠키(`SESSION`)로 준다. 프론트는 토큰을 다루지 않는다. 로그아웃은 `POST /api/v1/user/logout` |
| 로그인 화면 | 프론트(React) 저장소에 둔다. 백엔드에는 화면이 없다. 프론트가 생기기 전 로그인 시험은 API 테스트(`AuthApiTest`)와 curl로 한다 |
| 세션 저장 | DB. Spring Session JDBC, `auth.spring_session`·`auth.spring_session_attributes`(공식 스키마). 서버를 다시 켜도 로그인이 유지된다 |
| 세션 수명 | 마지막 요청 뒤 8시간 |
| 쿠키 | `SESSION`: HttpOnly, SameSite=Lax, HTTPS면 Secure. 화면과 API가 같은 주소라 CORS 없음(개발은 Vite 프록시) |
| CSRF | 쓰기 요청은 `XSRF-TOKEN` 쿠키 값을 `X-XSRF-TOKEN` 헤더로 보낸다. 로그인하면 값이 바뀐다 |
| 로그인 처리 | Spring `formLogin`이 아니라 직접 만든 JSON 컨트롤러. 로그인할 때 세션 ID를 바꾼다 |
| 세션 내용 | 사용자 ID, 역할, 금액 권한, 로그인 시각. 서버는 이것으로 권한을 판단한다 |
| 권한 변경·계정 중지 | 그 사용자의 `auth.users.tokens_valid_after`를 지금으로 기록한다(컬럼 이름은 그대로). 서버가 요청마다 계정을 DB에서 다시 보고, 그보다 먼저 로그인한 세션이나 사용 중지·삭제된 계정의 세션은 끊고 401 |
| 로그인 실패 | 없는 아이디·틀린 비밀번호·사용 중지 계정을 구분하지 않고 모두 401 `LOGIN_FAILED` |
| 첫 관리자 | 앱이 켜질 때 사용 중인 관리자가 없으면 환경 변수 `ADMIN_LOGIN_ID`·`ADMIN_PASSWORD`로 만든다. 처음 로그인하면 비밀번호를 바꿔야 한다. 개발 편의로 기본값 admin/1234를 두고, 실제 운영 전에 뺀다 |

## 3. 결정별 후보와 이유

### 3.1 인증 방식: 세션 로그인

| 후보 | 결과 |
|---|---|
| ADR-11 그대로 (Spring 확장으로 refresh token을 쿠키로) | 버림. 1절의 확장 코드 여러 개와 백엔드 로그인 화면이 필요하다. 화면 하나·서버 하나인 사내 앱에 인가 서버를 두는 비용이 크다 |
| 인가 서버 + JWT 유지, 그 앞에 BFF | 버림. 같은 앱 안에서 토큰과 세션을 둘 다 관리하게 된다. 다른 앱(모바일·외부 시스템)이 같은 토큰을 써야 할 때만 이득인데, 그런 요구가 없다 |
| **서버 세션 로그인** | **채택** |

- 브라우저 스크립트가 로그인 정보를 만지지 않는다. HttpOnly 쿠키만 쓰므로 스크립트 공격(XSS)이 있어도 로그인 정보를 읽어 가지 못한다. ADR-11에서는 access token이 브라우저 메모리에 있어 스크립트가 읽을 수 있었다.
- JWT의 장점은 "요청마다 DB를 보지 않는다"인데, 권한 변경·계정 중지를 바로 반영하려면(INV-80) 어차피 요청마다 DB를 봐야 한다. 그 장점이 남지 않는다.
- 로그아웃이 확실하다. 서버의 세션 행을 지우면 끝난다. JWT는 만료 전까지 살아 있어 별도 차단 목록이 필요하다.
- 나중에 회사 SSO(OIDC)가 필요해지면 서버가 SSO의 클라이언트가 되어 같은 세션을 만들면 된다. 프론트는 바뀌지 않는다.

### 3.2 로그인 화면 위치: 프론트

| 후보 | 결과 |
|---|---|
| 백엔드에 Thymeleaf 화면 | 버림. 라이브러리가 하나 늘고 화면 디자인이 두 저장소로 나뉜다. ADR-11의 Authorization Code 흐름 때문에만 필요했다 |
| 백엔드 정적 HTML·Spring 기본 화면 | 버림. 같은 이유. 기본 화면은 영어이고 꾸밀 수 없다 |
| **프론트(React) 화면 + JSON API** | **채택** |

- 세션 로그인은 다른 주소로 이동(리다이렉트)할 필요가 없다. 화면은 API를 부르기만 하면 되므로, 다른 화면과 같은 디자인·오류 표시를 쓸 수 있는 프론트에 둔다.
- 프론트가 아직 시작 전이라 그동안의 로그인 시험은 API 테스트로 한다(실제 쿠키·CSRF·세션 저장까지 확인).

### 3.3 세션 저장 위치: PostgreSQL (Spring Session JDBC)

| 후보 | 결과 |
|---|---|
| 서버 메모리(Tomcat 기본) | 버림. 배포하거나 서버를 다시 켜면 모든 사용자가 작업 중에 로그아웃된다. 배포 때마다 DB 백업 후 앱을 다시 띄우므로(기술 스택 3.1) 자주 일어난다 |
| Redis | 버림. 서버 한 대라 따로 둘 이유가 없고 운영할 것이 하나 늘어난다. 기술 스택 4절에서 쓰지 않기로 했다 |
| **PostgreSQL (Spring Session JDBC)** | **채택** |

- 이미 운영하는 DB에 테이블 2개만 더하면 된다. 백업도 DB 백업에 함께 들어간다.
- 나중에 서버를 늘려도 세션을 함께 쓴다.
- Spring Session 공식 스키마를 그대로 써야 Spring이 읽는다. 그래서 공통 규칙(UUID·감사 컬럼)의 예외로 둔다(테이블 정의서 3.2.1).
- 만료된 행은 Spring Session이 1분마다 지운다. 따로 정리 작업이 필요 없다.

### 3.4 세션 수명: 마지막 요청 뒤 8시간

| 후보 | 결과 |
|---|---|
| 7일 (ADR-11 refresh token과 같은 경험) | 버림. 공용 PC나 자리를 비운 PC에서 다음 날까지 로그인이 남는다 |
| 30분 | 버림. 점심·회의 뒤마다 다시 로그인해야 한다 |
| **8시간** | **채택** (2026-11-25 결정) |

- 하루 업무 시간 동안은 한 번 로그인으로 쓰고, 업무가 끝나면 끊긴다. 요청할 때마다 8시간이 다시 시작된다.

### 3.5 쿠키 속성

- **HttpOnly**: 스크립트가 세션 쿠키를 읽지 못하게 한다(3.1).
- **SameSite=Lax**: 다른 사이트에서 보내는 POST에는 쿠키가 붙지 않는다. Strict는 메일·메신저의 링크로 들어오면 첫 화면에서 쿠키가 빠져 로그아웃된 것처럼 보이므로 쓰지 않는다.
- **Secure**: HTTPS 요청일 때만 붙인다. 개발 PC(http://localhost)에서도 로그인이 되게 하기 위해서다. 운영은 Nginx가 HTTPS를 받으므로 앱이 이를 알도록 설정해야 한다(5절).
- **CORS 없음**: 화면과 API가 같은 주소(Nginx가 `/api`를 백엔드로 넘김)라 쿠키가 그대로 붙는다. 다른 주소에서 API를 부를 수 없게 하는 효과도 있다.
- Spring Boot 4.1에서는 `server.servlet.session.cookie.http-only` 설정을 줘도 Spring Session 쿠키에 HttpOnly가 붙지 않는 것을 확인했다(자동 설정된 쿠키 설정 객체 값이 false). 그래서 쿠키 설정을 코드(`CookieSerializer` 빈)로 직접 정하고 테스트로 확인한다.

### 3.6 CSRF: 쿠키 값을 헤더로 다시 보내기

- 브라우저가 쿠키를 자동으로 붙이는 방식이라, 다른 사이트가 사용자 몰래 쓰기 요청을 보내는 공격(CSRF)을 막아야 한다. SameSite=Lax가 대부분 막지만 브라우저마다 동작이 달라 CSRF 토큰을 함께 쓴다.
- 서버가 `XSRF-TOKEN` 쿠키(스크립트가 읽을 수 있음)를 주고, 프론트가 그 값을 `X-XSRF-TOKEN` 헤더로 보낸다. 다른 사이트는 우리 쿠키 값을 읽을 수 없어 헤더를 맞출 수 없다. Spring Security가 화면 앱(SPA)용으로 제공하는 방식이다.
- Spring은 토큰이 필요할 때만 만들기 때문에, 첫 응답에 쿠키가 나가도록 필터를 하나 더했다. 로그인 전에도 프론트가 토큰을 받아야 로그인 요청을 보낼 수 있다.
- 로그인하면 토큰을 새로 바꾼다. 로그인 전 토큰이 다른 사람에게 알려져 있어도 로그인 뒤에는 쓸 수 없게 한다.

### 3.7 로그인 처리: JSON 컨트롤러

| 후보 | 결과 |
|---|---|
| Spring `formLogin` | 버림. form 형식 파라미터만 읽는다. 성공·실패 응답을 우리 공통 형식(`ApiResponse`, 오류 코드)으로 맞추려면 처리기를 여러 개 바꿔 끼워야 하고, 입력 검사도 따로 해야 한다 |
| **직접 만든 컨트롤러** | **채택** |

- 다른 API와 같은 방식(JSON 요청, `@Valid` 입력 검사, 공통 응답 형식)으로 만든다.
- formLogin이 해 주던 보안 처리는 Spring 부품을 그대로 불러 빠뜨리지 않는다: 로그인할 때 세션 ID 바꾸기(남이 미리 정한 세션 ID로 로그인시키는 공격 방지), CSRF 토큰 바꾸기, 세션에 로그인 정보 저장.

### 3.8 권한 변경을 바로 반영: 요청마다 DB 확인

- 세션에는 로그인할 때의 역할·금액 권한이 저장된다. 관리자가 권한을 빼거나 계정을 중지해도 세션 안의 값은 그대로다. INV-80은 이것이 바로 반영되기를 요구한다.
- 그래서 요청마다 사용자 한 행을 기본 키로 읽어 사용 여부·삭제 여부·`tokens_valid_after`를 본다. 로그인 시각이 그보다 이르면 세션을 끊는다. 다시 로그인하면 바뀐 권한으로 일한다.
- 세션 행을 찾아 지우는 방식도 있지만, 관리자 기능마다 세션 삭제를 빠짐없이 넣어야 한다. 시각 하나를 기록하는 쪽이 빠뜨릴 곳이 적다.
- `tokens_valid_after` 컬럼은 이름을 바꾸지 않았다. 뜻("이 시각 전 로그인은 무효")이 그대로라 이름을 바꾸는 마이그레이션과 문서 수정을 만들 이유가 없다.
- 캐시는 두지 않았다. 사용자 수가 확정되면(ISS-10) 다시 본다.

### 3.9 로그인 실패를 구분하지 않음

- "없는 아이디"와 "틀린 비밀번호"를 다르게 알려 주면 어떤 아이디가 있는지 알아낼 수 있다. 그래서 모두 `LOGIN_FAILED` 하나로 답한다.
- 없는 아이디일 때도 비밀번호 해시 비교를 한 번 해서 응답 시간 차이로 구분되지 않게 한다.

### 3.10 첫 관리자: 환경 변수로 자동 생성

| 후보 | 결과 |
|---|---|
| 마이그레이션에 고정 계정 넣기 | 버림. 임시 비밀번호 해시가 Git에 남는다 |
| 운영자가 직접 SQL 실행 | 버림. 설치할 때마다 사람이 해야 하고 빠뜨리기 쉽다 |
| **앱이 켜질 때 환경 변수로 생성** | **채택** |

- 계정 만들기는 관리자만 할 수 있는데 처음에는 관리자가 없다. 그래서 앱이 켜질 때 사용 중인 관리자가 없으면 한 명을 만든다. 비밀번호는 다른 비밀 값처럼 환경 변수로 넣는다(NFR-01).
- 처음 로그인하면 비밀번호를 바꿔야 쓸 수 있다(API 명세서 1.14).
- 기본값 admin/1234는 아직 실제 운영 전이라 개발 편의로 둔 것이다(2026-11-25 결정). 운영 전에 기본값을 뺀다.

## 4. 영향

- DB: 마이그레이션 V3로 `auth.oauth2_authorization`을 지우고 세션 테이블 2개를 만든다. 테이블 정의서 3.2.1
- API 명세서 1.3절, 오류 코드 `LOGIN_FAILED` 추가, `Me`에 mustChangePassword
- API 목록: 로그인·로그아웃 경로를 `/api/v1/user/login`, `/api/v1/user/logout`으로 바꿈
- 권한 매트릭스, 백엔드 기술 스택, 디렉토리 구조의 토큰 설명을 세션으로 바꿈
- 프론트: 로그인 화면에서 JSON으로 보내고, 쓰기 요청마다 `X-XSRF-TOKEN` 헤더를 붙인다. 401을 받으면 로그인 화면으로 보낸다

## 5. 남은 일

- 운영 전 `ADMIN_LOGIN_ID`·`ADMIN_PASSWORD` 기본값 제거
- 운영 설정(`application-prod.yml`)에서 Nginx가 넘긴 HTTPS 정보를 앱이 믿도록 설정(`server.forward-headers-strategy`). 없으면 Secure가 붙지 않는다
- CSRF 실패를 `FORBIDDEN`과 다른 오류 코드로 나눌지 (프론트가 "토큰 다시 받기"를 구분해야 하면)
- 세션에는 로그인 정보 객체를 직렬화해 저장한다. 그 클래스를 옮기거나 필드를 바꾸면 저장된 세션을 읽지 못해 모두 다시 로그인해야 한다. 배포 때 알고 있으면 된다
